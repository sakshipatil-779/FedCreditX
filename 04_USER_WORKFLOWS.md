# 04 — User Workflows

## Workflow A — Start and inspect a training run (primary technical flow)

**User:** ML/engineering lead or federation administrator.

**Input:** generated synthetic training data split into three simulated lender partitions; common schema; run configuration; chosen privacy mode.

**Process:**
1. Open the training page.
2. Confirm three simulated clients and show the data partitions are local demo files/client resources.
3. Choose a run configuration: standard FL first; DP-enabled run only if DP is implemented and correctly configured.
4. Start the run.
5. Flower coordinates local model updates and global aggregation.
6. The app records status, rounds, active clients, aggregate evaluation metrics, model version, and privacy configuration.

**Verification:** run logs and tests confirm real client training and server aggregation took place. Metrics are generated by the run, not static placeholders.

**Output:** completed/failed training run, measurable metrics, and a run history item.

**Failure paths:** missing dataset, client failure, incompatible model state, non-finite loss, aggregation error, unsupported privacy option. The UI reports failure and does not label the run successful.

## Workflow B — Score and understand a synthetic applicant (primary user flow)

**User:** lending-risk analyst/underwriter.

**Input:** selected synthetic applicant ID from a simulated lender's local demo case file; current global model artifact.

**Process:**
1. Select a simulated lender.
2. Select a preloaded synthetic applicant. Do not type or upload real PII.
3. Request scoring through the selected lender's simulated local scoring workflow.
4. The selected client reads the applicant's local synthetic feature vector and runs model inference.
5. The app receives the prediction plus feature attribution/reason codes, without sending the training partition to the central service.
6. Show the model-estimated default probability and a clearly labelled demo risk band.
7. Show the top features that increased and decreased the prediction.
8. The analyst selects “Reviewed”, “Need more information”, or “Escalate for human review”. These are demo workflow states, not actual lending outcomes.

**Verification:** output maps to the current model version; explanation values are based on the real model output; the UI explicitly warns that attribution is not causation and model probability is not calibrated creditworthiness unless calibration is measured.

**Output:** case result, explanation, model version, timestamp, and review audit event.

## Workflow C — Compare the experiment

1. Open the metrics view.
2. Compare the centralised synthetic-data baseline and the federated global model on a defined held-out synthetic test set.
3. Show relevant metrics: ROC-AUC, precision, recall, F1, confusion matrix; mention class balance and threshold.
4. When valid DP is available, compare non-private and DP-enabled results and display actual privacy parameters/accounting if correctly calculated.
5. Explain that a synthetic benchmark is a feasibility demonstration, not proof of real-world performance.

## Workflow D — Inspect audit history

1. Open run/case history.
2. Filter by event type or run ID.
3. Inspect who/what initiated the event, timestamp, model version, status, and non-sensitive metadata.
4. Confirm no raw training rows or personal identifiers appear in the audit payload.

## Stranger test tasks

Give a person who has not heard the pitch these tasks without explaining the interface:

1. Start or inspect a training run and tell you whether it really completed.
2. Select a synthetic applicant and explain which factors moved the estimate up/down.
3. Explain what “raw data stays local” means in this demo and name one limitation.
4. Find the model version and audit event for the result.

Record every hesitation, incorrect click, incorrect assumption, and phrase they misunderstand. Do not guide them unless the test ends.
