# 06 — MVP Scope and Boundaries

## Minimum viable demonstration

One end-to-end flow must work:

**Generate synthetic lender partitions → train centralized baseline → run real Flower federation → inspect measured metrics → score a preloaded synthetic applicant at one lender → view model-derived explanation → record human review in SQLite.**

## In scope

### Core (P0)
- Three simulated lender partitions, generated reproducibly.
- Shared feature schema and documented preprocessing.
- PyTorch logistic regression; no deep learning.
- Flower federated training with at least one real aggregation round (target multiple rounds if feasible).
- A centralized synthetic benchmark for comparison.
- Synthetic case selection and scoring with the federated model.
- SHAP where supported; clear reason-code fallback.
- Next.js dashboard, FastAPI API, SQLite history/audit events.
- README, tests, sample screenshots or demo notes, known limitations.

### Privacy enhancement (P1/P2)
- Opacus DP local training, with valid configuration and privacy accounting, after base FL works.
- Flower SecAgg+ after the chosen Flower API pattern is verified compatible.
- Compare model quality across the actual privacy configurations that successfully run.

## Not in scope

- Real applicant data, bank statements, UPI records, PAN, Aadhaar, contact details, or other personal data.
- Live API connections to lenders, banks, bureaus, Account Aggregators, UPI, or payment providers.
- Real loan eligibility, approval, rejection, offers, interest rates, or customer-facing financial advice.
- A production grade access-control system or multi-tenant deployment.
- Blockchain or immutable/distributed ledger.
- Deep-learning architecture.
- LLM-generated decision reasoning or chat.
- Claims that model updates are inherently safe or raw-data locality provides perfect privacy.
- Comprehensive regulatory/compliance certification or fairness guarantees.

## Scope priority rule

If time becomes tight, cut features in this order:
1. Gemini/LLM and chat (already excluded from core).
2. SecAgg+ if compatibility/testability blocks the core; document not implemented.
3. Advanced charts, multiple admin roles, complex filters.
4. Custom authentication.

Never cut the genuine federated-training path, truthful explanations, synthetic-only data policy, or test evidence just to finish more screens.

## Acceptance checklist

- [ ] Reproduce datasets from a documented command.
- [ ] Show the three client partitions and explain that each is simulated.
- [ ] Complete and log a real Flower federated run.
- [ ] Show metrics actually generated by the run.
- [ ] Score a sample case via the selected simulated lender path.
- [ ] Display the model estimate with demo-only wording.
- [ ] Display feature contributions/reason codes from the actual prediction.
- [ ] Record and retrieve the human-review event.
- [ ] Pass test plan P0 cases.
- [ ] Clearly label DP/SecAgg+ as active, not active, or untested.
- [ ] Update README and `BUILD_LOG.md` with actual evidence.
